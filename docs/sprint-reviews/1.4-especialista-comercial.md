## Decisões tomadas e ligação com ADRs/princípios

### Escopo

- **Slot-filling estruturado, sem nutrição automatizada** (princípio ADR-014). Especialista coleta, marca qualificado, escala humano. Pipeline visual / scoring / follow-up são Fase 3+.
- **5 ações deterministas no LLM output:** `ask_next_slot`, `acknowledge_then_ask`, `mark_qualified`, `escalate_human`, `request_human_handoff`. Mapa fechado; saídas fora do enum viram parse error → escala humano (princípio: determinismo onde possível).
- **T10 (fechamento qualificado) é renderizado deterministicamente, não usa content do LLM**. Mesmo padrão de ADR-014/Coordenador: `respond_direct` usa template. Content do LLM em mark_qualified vai pra audit como `llm_rejected_content` pra eval futuro.

### Arquitetura

- **Coordenador continua subscrevendo `message.received` direto (ADR-019)**. Não normalizei o roteamento neste sprint. Especialista Comercial subscreve `agent.handoff_requested` filtrando `toAgentKey === 'atendimento.especialista_comercial'`. Cada agente tem seu canal de entrada — fonte de evento diferente, mesma idempotência por messageId.
- **Graph LangGraph com 3 nós + act externo** (espelha Coordenador, ADR-016): graph é puro (raciocínio), act é I/O. Pré-detect deterministico antes do LLM (skip LLM quando lead em estado terminal ou resposta de horário).
- **context.ts read-only** (ajuste do advisor review). Quem cria lead é `act.ts:ensureLead`. Mantém graph livre de side-effect.

### Integridade

- **Verificação de `mark_qualified` antes de aceitar** (ajuste do advisor review). Após merge dos slots extraídos, se `isQualified(merged) === false`, override pra `ask_next_slot` com pergunta canonical via `renderSlotQuestion`. Audit registra `mark_qualified_overridden`. Sem isso, Haiku iria eventualmente disparar T10 com lead pela metade.
- **Auto-promote inverso:** se LLM diz `ask_next_slot` mas merge dos slots completou qualificação, materialize redireciona pro fluxo de mark_qualified. Cobre o caso de LLM extrair último slot mas não perceber.

### Estado de qualificação

- **Lead vive em tabela própria, não em conversation.metadata** (princípio "estado canônico compartilhado"). Cada turno carrega fresh do banco; agente é stateless. Permite múltiplos workers paralelos sem race no estado interno (race no INSERT inicial fica como TD-023).
- **`primary_contact_id` UUID sem FK**: tabela `contacts` não existe em main. TD-021 documenta migration aditiva quando tabela existir.
- **Sem `account_id` em leads**: lead inherita via `primary_conversation_id → conversation.account_id`. `converted_to_account_id` é o campo semanticamente correto pra transição lead→account.

### Detecção de horário

- **Tokenização por whitespace + check de set + regex pra horários explícitos.** Tentei `\b` Unicode-aware primeiro mas falhou em palavras com acentos/cedilha (ç/ã). Approach atual é robusta o suficiente pra Fase 1; parser→Date é TD-024.
- **Pre-detect em `qualified` + schedule hint → skip LLM**. Direto pra `scheduled_pending` + T10b. Bot não roda LLM nesse turno.
- **Pre-detect em `scheduled_pending` → silent_handoff** sem mensagem outbound. Bot não responde mais — humano cuida.

## Performance do Haiku 4.5

- **Eval estrutural (replay, LLM mockado):** 28/28 fixtures = 100% accuracy estrutural. Pipeline (pre-detect + parse + normalize) processa o esperado.
- **Custo real médio por turno (estimado):** Haiku 4.5 a ~$0.001 por chamada (system ~600 tokens + user ~50 tokens + output ~150 tokens). Mais barato que Sonnet do Coordenador (~$0.003), apropriado pra slot-filling.
- **Latência média:** não medida nesta sprint (requer LLM real). Esperada 1-2s por turno.
- **Decisão:** manter Haiku. Promover pra Sonnet só se eval real (TD-015 expandido pra Especialista) revelar accuracy < 70% — registrar como TD adicional nesse caso.

## Riscos residuais

1. **Lead duplicado em race extremo (TD-023):** dois turnos quase-simultâneos antes do primeiro commit. Volume Fase 1 não dispara; documentado.
2. **Schedule detection false-positive:** mensagem "tarde demais" pode disparar schedule_response. Heurística tokenizada minimiza falsos mas não elimina. Cliente recebe T10b — ruim, mas humano corrige rapido pela UI quando ver lead em scheduled_pending sem horário real.
3. **Haiku eventualmente alucina mark_qualified com slots incompletos:** mitigado por verificação `isQualified(merged)` antes de aceitar. Override registrado em audit.
4. **`responsavel_name = signature`** soa esquisito ("Vou agendar com Equipe X, que vai te entender melhor"). Aceitável Fase 1; TD-025 cuida.
5. **Database.types.ts editado à mão** (TD-012 ainda aberto): mesma situação do Sprint 1.2. Resolução continua sendo "rodar `pnpm db:types --linked` após aplicar migrations no cloud".
