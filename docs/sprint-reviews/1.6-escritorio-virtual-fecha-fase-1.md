## Decisões tomadas e ligação com ADRs/princípios

### 1. Não criar eventos novos `agent.processing`/`agent.idle`

- **Motivação:** o sprint pediu eventos novos pra "estado lógico atualizado em tempo real", mas a inspeção do código revelou que `agent.state_changed` já flui worker → UI (`apps/agent-runtime/src/workers/agent-tasks.ts:225,261` publica; `apps/web/src/components/realtime-provider.tsx:161` consome via `updateAgentState`). Selector `useAgent(id).state` já vira `'working'` durante processamento.
- **Ligação:** Princípio 1 (plataforma, não produto — reusa contrato existente em vez de duplicar). ADR-002 (sem dependências entre agentes — manteve canal único de mudança de estado).
- **Desvio do prompt:** sim, documentado. Sprint pedia eventos novos; entreguei reuso do existente.

### 2. Pulse visual aplicado ao sub-container `avatar` (body+ring), não ao container raiz

- **Motivação:** sprint pediu "escala suave 1.0 → 1.05 → 1.0". Aplicar no container raiz esticaria a label do agente — visualmente quebra. Sub-container `avatar` agrupa body+ring, pulsa em conjunto, label fica estável.
- **Ligação:** Princípio 3 (determinismo onde possível — pulse é trivial sem LLM). Trade-off: 1 nível a mais de hierarquia no Pixi.

### 3. Animação de handoff dispara via Zustand store separado + drenagem após dispatch

- **Motivação:** RealtimeProvider está em `dashboard/layout.tsx`, OfficeCanvas em `dashboard/escritorio/page.tsx`. Sem store global, dispatch passaria por window event ou ref imperativo via context. Store dedicado (`handoff-animation-store.ts`) mantém realtime-store enxuto e dá pra testar a fila isoladamente.
- **Limite de 5 animações concorrentes:** descarta extras com log. Adequado pra volume Fase 1; reabrir como TD se rajada virar problema real.
- **Ligação:** ADR-002 (separação de responsabilidades entre stores).

### 4. HUD da sala Atendimento é fixo (não viewport-aware)

- **Motivação:** sprint autorizava fallback se detecção complexa. Canvas atual não tem zoom/pan, então "câmera focada na sala" não existe.
- **Trade-off:** quando outros departamentos entrarem com HUDs próprios, vão se sobrepor visualmente. TD-033 documenta solução posterior junto com navegação de câmera.

### 5. Página de detalhe de conversa é read-only

- **Motivação:** envio manual pelo operador está fora do escopo da Fase 1 (sprint explicita). Página entrega timeline + sidebar com intent, classifications, lead, drafts vinculados. Pra agir sobre draft, link manda pro inbox.
- **Ligação:** Princípio 4 (human-in-the-loop em ação externa — operador continua decidindo só via inbox de drafts; página de detalhe não cria novo caminho de send).
- **`messages` NÃO entrou no realtime store global** (advisor sinalizou). Hook local na própria página refetcha via endpoint `GET /api/atendimento/conversations/[id]` quando socket avisa `message.received` filtered. Evita poluir o store com entidades de alta cardinalidade.

### 6. Onboarding redirect estrito `display_settings.onboarding_completed === false`

- **Motivação:** sprint tinha contradição interna ("tenant já existe sem wizard, app funciona normal" vs redirect "se false (ou ausente)"). Interpretação coerente: marcar `false` SÓ em tenants novos (via `createTenant` agora retorna `{ tenant, created }` e webhook/complete-org marcam pending apenas se `created === true`), redirect estrito `=== false`. Tenants legados ficam `undefined` e passam direto.
- **Trade-off documentado no commit:** `createTenant` mudou de upsert pra lookup-then-insert pra distinguir criação. Race entre Clerk webhook + onboarding síncrono retorna `created: false` no segundo via `23505`.
- **Ligação:** Princípio 7 (autonomia em tiers — wizard configura tier inicial por agente; default sugestivo).

### 7. Modo demo: gate único `isDemoModeEnabled()`; auto-login fica como TD

- **Motivação:** sprint tinha ambiguidade no gate de produção. Helper único `isDemoModeEnabled(env)` resolve: dev sempre, prod só com flag explícita. Endpoint `/api/demo/trigger-scenario` e rota `/demo` checam o mesmo helper.
- **Auto-login não implementado:** sprint autoriza fallback. Levi loga normal e seleciona "Demo — Levi Lael" no Clerk Org Switcher. TD-034 documenta.
- **Seed cria Clerk org real** via fetch direto na API Clerk (não SDK pra não puxar @clerk/backend pro script). Requer `CLERK_DEMO_OWNER_USER_ID` + `CLERK_SECRET_KEY`.

### 8. Suite de polimento UX: 3 utilitários compartilhados + aplicação seletiva

- **Motivação:** sprint listava 7 itens (a-g). Em vez de reescrever cada página, criei `EmptyState`, `ListSkeleton`/`BlockSkeleton`, e `humanErrorMessage` reusáveis. Aplicação seletiva: DraftsInbox (skeleton + EmptyState), `/inbox/page.tsx` (toast + humanErrorMessage), Leads/Canais (skeleton + EmptyState), ConversationDetailView (error banner inline com humanErrorMessage).
- **Tooltips via `title` atributo nativo cobre 80%.** Refactor pra Radix Tooltip ficaria TD se UI escalar — não justifica nesta sprint.

### 9. Hotfix de `.js` extensions em shared-config

- **Detecção:** `pnpm build` quebrou após T7 introduzir import de `isDemoModeEnabled` em `/demo/page.tsx`. Mesmo padrão do TD-013 (shared-domain) já fechado. Hotfix mecânico: remover `.js` de 2 imports.
- **Diagnóstico de por que typecheck/test não pegou:** vitest e tsx aceitam `.js` literal; webpack do Next não. Single source da verdade pra moduleResolution continua sendo TD-013 (no Fase 2-prep).

## Riscos residuais identificados

1. **`createTenant` mudou semântica (upsert → lookup-then-insert).** Outros callers de `createTenant` (webhook Clerk, complete-org) atualizados. Mas qualquer código fora do monorepo que chame `createTenant` espera a versão antiga. Como é monorepo interno, baixo risco; documentar no diff.

2. **Demo tenant precisa CLERK_DEMO_OWNER_USER_ID válido.** Se rodar com `user_xxx` que não existe, fetch Clerk falha. Script valida que começa com `user_` mas não que existe. Aceitável — primeira execução vai falhar com erro claro do Clerk.

3. **Animação de handoff descarta extras acima de 5 concorrentes.** Em volume Fase 1 isso nunca acontece. Quando tier `autonomo` entrar em departamentos com alta vazão, rever.

4. **Onboarding wizard valida no client mas Zod no servidor faz validação dupla.** Inconsistência minor: se cliente submete payload manipulado (devtools), Zod rejeita. Comportamento OK.

5. **Página de detalhe de conversa refetch em cada draft.* event.** Se conversa tem 50 drafts e operador aprova rápido, refetch dispara várias vezes seguidas. Custo da API GET (que faz 4 selects paralelos) é baixo, mas pode ficar visível em conexões lentas. Aceitável Fase 1.

5b. **`ConversationDetailView` abre seu próprio Socket.io connection separado do `RealtimeProvider`.** Cada visita à página de detalhe = +1 conexão (com seu próprio handshake JWT). Overhead duplicado mas funcional pra volume Fase 1. Quando segundo departamento entrar com várias páginas de detalhe paralelas, consolidar via channel filter no provider único (subscribe selectivo por conversationId).

6. **DemoTriggerWidget endpoint require auth com `orgId` (org ativa no Clerk).** Se Levi acessa `/demo` mas ainda não trocou pra "Demo — Levi Lael", endpoint retorna 401. UI mostra mensagem clara, mas seria mais elegante detectar e pedir switch.

## Surpresas durante implementação

1. **Evento `agent.state_changed` JÁ EXISTIA e fluía worker→UI.** O sprint pedia eventos novos `agent.processing`/`agent.idle` — escopo de T1 ficou bem menor que o prompt sugeria. Documentei como decisão consciente.

2. **`createTenant` precisava distinguir create vs upsert pra T5 funcionar coerentemente.** Mudança de upsert pra lookup-then-insert. Risco: outros callers. Auditei: só 2 (webhook + complete-org), ambos atualizados na mesma sprint.

3. **`.js` extension em shared-config quebrou build** depois de T7 — mesma cabeça do TD-013 já fechado em shared-domain. Diagnose: vitest/tsx aceitam, webpack Next não. Hotfix mecânico no fim, mas reforça que TD-013 (moduleResolution unificada) precisa subir prioridade.

4. **`messages` NÃO entrou no realtime store global.** Advisor sinalizou; tomei como decisão arquitetural. Hook local refetcha via endpoint na página de detalhe. Mantém store focado em entidades de baixa cardinalidade.

5. **`getLeadByConversationId` requer tenantId** que não está no auth context server-side direto. Substitui por select direto + RLS no `loadConversationDetail` — mais limpo que carregar tenant_id extra.

6. **Sprint 1.3 tinha 3 TDs (catálogo, storage, RLS suite) que ficaram só no self-review.** Descoberta durante T8 (consolidação). Persistidos como TD-030, TD-031, TD-032. Sprint 1.5 já mencionou esse padrão pra TD-021 do 1.3.

7. **Polimento UX gastou MUITO menos tempo que esperado.** 3 utilitários compartilhados + aplicação seletiva resolveu 80% do valor. Sem refactor de Toast pra Radix Tooltip — `title` nativo cobre na prática.

8. **PixiJS v8 API confirmada sem surpresa.** Ticker, Application, Container, Graphics, Text seguem documentação. Pulse via `Math.sin(elapsed * 3) * 0.05` aplica oscilação de 5% sobre scale 1.0 — visualmente sutil.

9. **Permissão assimétrica detectada por review final.** `/api/onboarding/atendimento` chamava `updateAgentAutonomyTier` (que muda comportamento sistêmico) sem o role check que existe no endpoint irmão `/api/configuracoes/agentes/[id]` desde o Sprint 1.5. Em fluxo normal o caller é o `owner_tenant` (criador da Clerk org) então passaria sempre — mas a assimetria era exploitável: basic_member adicionado durante onboarding pendente poderia POST-ar direto no endpoint do wizard pra alterar tier mesmo sem permissão pelo endpoint regular. Adicionado `getCurrentTenantUserRole` + `ALLOWED_ROLES = {owner_tenant, manager}` antes do push, simétrico ao endpoint irmão.

10. **`tenantNeedsOnboarding` precisava de testes.** Função pura crucial pro fluxo de redirect — refactor futuro pra `!completed` quebraria silenciosamente o comportamento de tenants legados. 8 testes adicionados em `packages/shared-domain/src/tenants/__tests__/onboarding.test.ts` cobrindo `=== false` estrito vs falsy values.
