## Decisões tomadas e ligação com ADRs/princípios

### 1. Criar schemas mínimos `obligations` + `documents` dentro do sprint (em vez de degradar Especialista)

- **Motivação:** spec parou explicitamente em "PARE se as tabelas não existirem". Apresentei opção A (criar schemas) vs B (degradar Especialista) ao Levi. Decisão dele = A. Schemas são puro storage, sem cálculo de imposto embarcado. `type`/`category` como TEXT com CHECK em `category` apenas — variedade de obrigações brasileiras inviabiliza enum estável.
- **Ligação:** Princípio 2 (estado canônico compartilhado). Princípio 1 (plataforma — Sprints 1.5+, Fase 2 Societário, Fase 3 Pessoal reusam essas tabelas). ADR-014 deixa explícito que Fase 1 não integra sistema contábil legacy — schema mínimo é coerente com escopo.
- **Critério de evolução:** quando integração com Domínio/Alterdata/etc entrar (Fase 2+), refatoração é aditiva (campos novos, sem renomear).

### 2. Especialista subscreve `agent.handoff_requested`, não `message.received`

- **Motivação:** ADR-016 separa Coordenador (camada 2) de Especialista (camada 3). Especialista só roda quando o Coordenador já classificou intent operacional e despachou via evento. Reusa o pattern do Coordenador (Sprint 1.2).
- **Ligação:** ADR-016. Sprint 1.3 valida camadas 2→3 do modelo em produção.

### 3. Bypass de Roteador global mantido (ADR-019)

- **Motivação:** ADR-019 é explícito: na Fase 1, Coordenador subscreve `message.received` direto. Sprint 1.3 NÃO mexe nisso. Especialista entra na cadeia depois do Coordenador via `agent.handoff_requested` — coerente com a topologia atual.
- **Critério de revisão:** quando segundo departamento (Societário) entrar (Fase 2), Roteador entra como pré-requisito. Cadeia inteira muda no mesmo sprint.

### 4. "Draft + envio direto" no tier sugestivo da Fase 1 (desvio temporário de ADR-017)

- **Motivação:** ADR-017 prescreve tier sugestivo = "draft pending bloqueia até aprovação humana". Implementar essa semântica completa exige UI de inbox + worker de expiração + lógica de re-envio + edição. Trabalho que está planejado pro Sprint 1.5.
- **Decisão pragmática Sprint 1.3:** tier sugestivo = "cria draft com status `auto_approved` + envia mensagem direto". Mantém rastreabilidade (audit_log + message_drafts.final_message_id) sem inflar escopo.
- **Critério de reabertura:** Sprint 1.5 implementa UI de inbox + worker de expiração; mudar comportamento de `auto_approved` → `pending` real. **TD-021 criado.**

### 5. Curto-circuitos pré-LLM no handler (defesa em profundidade)

- **Motivação:** sem account vinculada OU intent always-human (`operacional.duvida_regime`, `urgente`, `requer_humano`) → handler escala direto sem chamar LLM. Salva ~USD 0.01 por mensagem nesses casos + reduz latência.
- **Ligação:** ADR-014 (Especialista read-only — sem account não opera). Princípio 4 (HITL em ação externa de impacto).
- **Trade-off:** duplica lógica entre Coordenador (que já escala `operacional.duvida_regime` por catálogo) e Especialista. Aceito como defesa — se Coordenador tiver bug e despachar mesmo assim, Especialista pega.

### 6. Tools sempre gravam audit_log (ADR-006 + auditability.md)

- **Motivação:** cada tool registra `tool.read.<nome>` no audit_log com `account_id` e `actor`. Permite reconstruir "que dados foram consultados pra gerar esta resposta". Importante pra LGPD + regulatório.
- **Ligação:** ADR-006 (audit_log INSERT-only) + regra `.claude/rules/auditability.md`.

### 7. `T_NO_DATA` é caminho de escalação (não de respond)

- **Motivação:** quando todas tools retornam vazio, agente escala humano com `T_NO_DATA` como mensagem-ponte ao cliente. Conversation fica marcada `assigned_to_human=true` independente — `T_NO_DATA` é a notificação ao cliente, não uma resposta de fato. `act.ts` decide entre T05 (default) e T_NO_DATA baseado em palavra-chave no `escalation_reason`.
- **Ligação:** Princípio 3 (determinismo onde possível, IA onde necessário) — escalar com mensagem informativa é determinístico depois da decisão do LLM.

### 8. Tipos do Database adicionados manualmente em `database.types.ts` (sem rodar `pnpm db:types`)

- **Motivação:** Docker não está rodando localmente. `pnpm db:migrate` + `pnpm db:types` exigem Supabase local up. Em vez de bloquear o sprint, adicionei types manualmente espelhando exato o que as migrations criam. Quando Levi rodar local com Docker up, `pnpm db:types` regenera e qualquer diff aparece.
- **Risco:** typo em algum campo que não pegamos no typecheck. **Mitigação:** Levi roda `pnpm db:migrate && pnpm db:types` antes do push pra confirmar sintaxe do SQL e alinhar types automaticamente.
- **Não é um desvio de ADR**; é uma limitação de ambiente de execução.

## Desvios intencionais

### TD-021 — "Draft + envio direto" temporário no tier sugestivo (Fase 1)

- **ADR afetado:** ADR-017 ("Modo shadow e tiers de autonomia em conversa síncrona")
- **O que foi feito:** Especialista grava draft com `status='auto_approved'` E envia mensagem direto via ChannelAdapter no tier sugestivo. ADR-017 prescreve `status='pending'` com bloqueio até aprovação humana.
- **Motivo:** UI de inbox + worker de expiração + lógica de re-envio são trabalho de Sprint 1.5. Implementar tudo aqui inflaciona escopo demais.
- **Quando reabrir:** Sprint 1.5 entrega UI de inbox completa, worker de expiração, edição de draft. Comportamento muda pra `pending` real, e o "auto_approved" passa a aparecer só em tier semi-autônomo (ADR-017 original).

### TD-022 — Tipos do Database mantidos manualmente até `pnpm db:types` rodar

- **O que foi feito:** Adicionei entries de `obligations`, `documents`, `message_drafts` em `packages/shared-db/src/database.types.ts` manualmente. Levi precisa rodar `pnpm db:migrate && pnpm db:types` antes do push pra confirmar fidelidade ao schema real.
- **Motivo:** Docker não rodava no ambiente.
- **Quando fechar:** assim que Levi rodar `pnpm db:types` e confirmar zero diff (ou aplicar diff e atualizar testes que dependem do schema).

### TD-023 — Catálogo de tipos de `obligation`/`document`

- **O que foi feito:** `type` em ambas tabelas é TEXT livre. CHECK só em `category`. Especialista (e Coordenador no futuro) interpretam `type` como string sem validação.
- **Motivo:** variedade enorme de obrigações brasileiras (federal/estadual/municipal/trabalhista). Enum vira fonte de manutenção constante. Sem urgência na Fase 1.
- **Quando reabrir:** Fase 2+ quando integração com sistema contábil legacy entrar e fornecer catálogo canônico.

### TD-024 — Storage de arquivos para documents

- **O que foi feito:** `storage_path` é opcional, sem integração com Supabase Storage real. Documentos podem ser registrados como "cliente disse que enviou X" sem o binário.
- **Motivo:** integração Storage + parsing (OCR de PDF, leitura de XML de NFe) é Fase 2+. Especialista da Fase 1 só lê metadata.
- **Quando reabrir:** Fase 2 (Fiscal) onde processamento de NFe vira primário.

## Riscos residuais identificados

1. **Types manuais vs schema real.** Se houver diff entre o que eu adicionei em `database.types.ts` e o que `pnpm db:types` gera depois, testes que dependem do shape vão quebrar. Mitigação: rodar `db:types` antes do push.

2. **Especialista pode entrar em loop com Coordenador se intent for ambíguo.** Cenário: Coordenador classifica `operacional.status_obrigacao` → Especialista escala humano com motivo "tipo de obrigação fora do regime" → conversation fica marcada `assigned_to_human=true`. Próxima mensagem do cliente sem operador respondendo → Coordenador reclassifica → enviou pra Especialista de novo. **Não previne loop hoje.** Mitigação parcial: `assigned_to_human=true` no metadata da conversation poderia ser checado pelo Coordenador (não está hoje). TD a abrir? **Vou deixar registrado mas não criar TD formal — depende de UX da Sprint 1.5 (operador vê inbox e responde).**

3. **`storage_path` em documents sem integração real.** Especialista pode acabar dizendo "recebi sua NF" baseado em row que existe sem arquivo real. Mitigação: Especialista usa `description` e `status` do document, não tenta abrir o arquivo. Fase 2+ resolve.

4. **Sem teste de isolamento entre tenants pras tools novas.** `getAccountSnapshot` valida tenant_mismatch, mas testes só cobrem caminho "ok" + tenant_mismatch local — não há teste de integração com 2 tenants concorrentes. Mitigação: RLS no schema + filtro explícito nas tools. Teste de integração formal pode ser adicionado em pacote separado.

3. **`reference_date` em documents pode ser null (atemporais).** Tive que decidir: filtro de janela `from/to` aplica só quando caller passa explicitamente. Sem from/to, lista os mais recentes por `created_at`. Caller decide se quer janela.

4. **AccountSnapshot é central — definição precoce no `shared-domain/atendimento/tools/types.ts` paga depois.** Vários módulos consomem (graph, act, context, formatting, testes).

5. **Refinements do Zod no schema do output do LLM (escalate_human exige escalation_reason, respond exige content) são suficientes pra robustez.** Eval cobre casos onde LLM viola refinement → schema falha → handler escala automaticamente. Não precisei adicionar lógica extra.
